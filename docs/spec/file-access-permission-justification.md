# 文件持久化权限申请理由

## 一句话理由（表单短文本）

木笺 MuMark 是离线 Markdown 编辑器。用户通过系统文件选择器打开外部 Markdown/HTML 文件后，应用需要持久保留对该文件的访问授权，才能在下次启动时继续编辑并原位保存同一个文件；不申请该权限将无法实现“打开的是原文件、保存后仍是原文件”的核心功能。

## 应用信息

| 项目 | 内容 |
|---|---|
| 应用名称 | 木笺 MuMark |
| 包名 | `com.mumark.app` |
| 版本 | 1.0.0 |
| 应用类型 | 效率 / 文档编辑，完全离线 |

## 申请权限

- **权限名**：`ohos.permission.FILE_ACCESS_PERSIST`
- **权限级别**：normal；**授权方式**：system_grant（API 11 及以上）
- **权限用途**：仅持久化用户在系统文件选择器中明确选择的单个文件或目录 URI 授权，不获取任何额外存储范围。

## 业务场景

1. 用户从“打开文档”、拖入或系统分享入口选择一个外部 `.md` / `.html` 文件。
2. 应用读取该文件并在编辑器中打开；自动保存或手动保存时写回同一个 URI。
3. 用户关闭应用后再次打开“最近文档”，应用需要恢复该 URI 的读写授权，直接继续编辑原文件。
4. 编辑过程中用户通过系统选择器插入本地图片或 HTML 资源；这些资源复制到应用私有附件目录用于离线预览和导出，不回写外部文件所在目录。

## 为什么必须持久化

- 系统文件选择器返回的 URI 授权默认是临时的，应用重启后失效。没有 `FILE_ACCESS_PERSIST`，每次启动都必须让用户重新选择同一个文件，否则无法读取和保存。
- 重复选择会带来版本混淆和重复副本：用户可能误选旧文件或另存副本，违背“打开原文件、保存原文件”的产品承诺。
- 最近文档、恢复草稿和外部文件冲突检测都以同一个 URI 作为文档身份；授权丢失会导致恢复链路断裂。

## 最小化使用与边界

- 只对用户主动选择并确认的 URI 调用 `fileshare.persistPermission` / `activatePermission`；不遍历目录、不扫描存储、不访问未选择的文件。
- 不申请 `INTERNET`，不上传任何文件或内容；全部处理在本机完成。
- 不申请宽泛的存储或媒体读写权限。该权限只延长“用户已授权的 URI”的有效期，不扩大授权范围。
- 附件复制仅发生在用户主动插入图片/HTML 时，目标为应用私有目录；不修改外部原文件所在目录的其他文件。
- 日志不记录正文、文件路径全文或剪贴板内容。

## 权限被拒绝或撤销后的行为

- 外部文件授权失效、文件被移动或删除时，编辑器进入“无法访问文件”状态并提示用户重新选择，不会静默写入其他文件。
- 用户可在系统设置中随时撤销授权；撤销后应用仍可使用应用内“我的文档”，外部文件需重新选择。
- 写入前会重新读取磁盘并做版本/哈希比对；检测到外部修改时进入冲突处理，不覆盖用户未确认的改动。

## 替代方案不可行

- **复制到应用沙箱**：会产生副本，后续修改不再作用于原文件，违背核心产品原则。
- **每次启动重新选择**：用户体验不可接受，且容易误选或产生副本；系统选择器已提供持久授权能力，重复选择不是最小必要方案。
- **申请宽泛存储权限**：超出实际需要，违反最小权限原则；本应用只需要用户已选择文件的持续访问。

## 合规承诺

本应用仅在上述场景使用该权限，不将权限用于收集、分析、上传或共享用户文件，不访问与用户选择无关的文件。授权可被用户随时撤销。可提供安装包和操作录屏供审核复现。
